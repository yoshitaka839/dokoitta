# note用の記録（「どこいった？」開発記）

Built with Claude: Japan 2026 ハッカソン作品「どこいった？」を作った過程を、あとで note の記事にするための記録です。
細かい失敗と修正は [試行錯誤の記録](./試行錯誤の記録.md) にあります。ここではその背景にある「なぜそう決めたか」「計画がどう変わったか」「Claude Code の機能をどこで使ったか」を中心に残します。

> 公開リポジトリなので、家族の実名・住所・実際の生活の詳しい話は書きません。記事にだけ使いたい個人的なエピソードは、公開されない `.private/note用メモ.md` に分けて書きます。

---

## 記事の骨組み（案）

1. きっかけ: 父が毎日眼鏡を探している
2. 作るものを決める: 「記憶に頼らない」探し方
3. Claude と一緒に設計する: まずコードを書かずに案を出してもらった
4. 役割分担: プログラムが候補を出し、Claude は順番を入れ替えて理由を一言
5. 公開リポジトリと家族の情報を守る仕組み（フック）
6. 声の聞き取りとの格闘（iPad 実機）
7. 父に試してもらった日
8. 振り返り: Claude Code の機能の使い分け、うまくいったこと・いかなかったこと

## 時系列

時刻は日本時間です。

### 2026-11-02（月）午後　初日: 設計とリポジトリの準備

- **14:10 作業場所を決めた。** クラウドではなく、自分の Mac のフォルダ（dokoitta）で作業してもらうことにした。
- **14:12 作るものを Claude に伝えた。** ハッカソンのルールで以前のコードは使えないので、この日から新しく書く。最初のお願いは「いきなりコードを書かずに、仕組みの案と作る順番を短くまとめて確認させて」。
  - 伝えた大事な流れ: ①手がかりがあればそれで探す ②思い出せなければ質問を重ねず、順番に確かめる（最初は頭の上・首元・服のポケット）③見つからなければ探した場所を残し、続けるか休むか選べる。家族も後から見られる。
  - 「必ず見つかる」とは言わせない。
- **14:13 Claude の最初の案。**
  - iPad の Safari で開く Web アプリ（Next.js）。ホーム画面に追加すればアプリのように使えて、App Store の審査もいらない。
  - 声の聞き取りと読み上げは iPad に入っている機能を使い、同じ操作をボタンでもできるようにする。
  - API キーはサーバー側だけに置き、iPad には届かない作り。
  - 「次にどこを確かめるか」はプログラムのルールで決める（いつもの置き場所、時間帯、過去に見つかった場所で点数）。言い過ぎを防ぐため。
- **14:24 案に3点の修正を入れて承認した。**
  1. **日程の修正。** 11/3 と 11/8 は作業できず、11/7 は半日。作業日は 11/2午後・11/4・11/5・11/6・11/7半日。11/6 に父に iPad で試してもらいデモ動画を撮る。声の聞き取りが一番不安なので、できるだけ早く iPad で試したい。
  2. **Claude の役目を広げた。** 候補と点数はプログラムで決めるのは賛成。そのうえで、父の話（「さっき新聞を読んでいた」など）を聞いて、**候補の中から**順番を入れ替え、理由を一言そえる役を Claude に任せる。候補にない場所は言わせない。返事は速いほうがいいので、モデルも目的に合わせて提案してもらう。
  3. **Claude Code の機能を目的に合わせて使う。** 審査基準に「Skills、サブエージェント、MCP、フックなどを目的に応じて使い分けているか」があるため。まず、GitHub に送る前に API キーや父の実際の情報が入っていないかを自動で確かめるフックを入れたい。
- **14:26 Claude の回答と準備。**
  - 日程の組み直し: 11/2 は準備と「声の聞き取りだけを試す小さなページ」を iPad で試すところまで。11/4 に①②③の流れと Claude による並べ替え、11/5 に記録と家族ページ、11/6 に父の試用とデモ動画、11/7 午前に仕上げと提出。

  - ほかの機能の使い道の提案: Skill は試行錯誤の記録を決まった形で追記するため。サブエージェントは言い回しを高齢者向けの視点で見直す役。MCP は GitHub 連携と、iPad の画面サイズで動作を確かめる Playwright。
  - つまずき: Claude の側からは GitHub のリポジトリを作れなかったので、自分で空の公開リポジトリを作ることになった。
- **14:29 この記録を始めた。** 後日 note で発表できるよう、全部記録してほしいと頼んだ。
- **14:37 最初のコミットを GitHub に送った**（自分で空の公開リポジトリを作ったあと）。送る前に、送信前チェックを通している。
  - つまずき: Mac 側の作業環境からは npm が 403 で使えなかった。そこで、部品の取得とビルドは Claude のクラウド側で行い、ソースだけを Mac のフォルダに同期する形にした。
  - 次のお願いは「Vercel で dokoitta を Import して」。iPad で試すには公開先が必要なため。
- **14:39 声の聞き取りだけを試すページ（/voice-test）を作った。** iPad の Safari に入っている聞き取りと読み上げの機能だけを使い、声はサーバーに送らない。iPad では読み上げもボタンを押した操作の中で始めないと鳴らないため、ボタンを押したときに一度呼ぶようにした。聞き取れた文字と、下の「記録」欄をスクリーンショットで送ってもらう約束にした。
- **15:11 Vercel に公開できた。** ただ Claude の作業環境からは公開したページを直接開けない設定で、画面は見られない。ここから先は「iPad で試す → スクショを送る → Claude が直す」の往復になった。

#### iPad での声のテスト（この日いちばんの山場）

- **15:52 1回目のテスト（スクショ）。** 聞き取りも読み上げも iPad の Safari で動いた。一番不安だった部分が初日に動いたのは大きい。ただ気になる点が2つ。
  - 失敗1: 「眼鏡、どこいった？」が「メガネ」と「どこいった」の2回に分かれて届いた。「、」のところの短い間で聞き取りが終わってしまう設定だったため。→ 聞き続ける設定にして、1.5秒黙ったらアプリ側で区切る方式に変えた（前の方式にも切り替えて比べられる）。高齢の人の話し方は間が空きやすいので、記事でも触れたい。
  - 失敗2: 「眼鏡」がカタカナの「メガネ」で返ってきた。→ どの書き方でも同じものとして扱う処理（lib/normalize.ts）を入れた。
  - 記録には、話していないはずの「聞いてます」という言葉も残っていた。Claude は「実際にそう話しましたか？」と聞き返した。
  - 発見: iPad の Safari は自分を「Macintosh」だと名乗るので、端末の種類の判定には使えない。
  - 話し始めてから聞き取りが確定するまで 4.7〜5.6 秒（話している時間を含む）。
- **15:56〜15:59 2回目のテストと、謎の「聞いてます」の正体。** 父が、画面のボタンに出ていた「聞いています」という字を、そのまま声に出して読んでいた。画面の字は「読むもの」として受け取られる。
  - → 逆にこれを活かし、聞き取り中のボタンには話してほしい言葉そのもの「眼鏡、どこいった？」を出すことにした。読み上げてもらえば、それが正しい入力になる。
  - 失敗3: 送ったスクショは記録の形が前のままで、iPad で再読み込みせず古い版で試していたことがわかった。→ タイトルの下に「版」（コミット番号）を出して、どの版で試しているか一目でわかるようにした。
- **16:03 3回目のテストで、声入力のめどが立った。** 父は画面の言葉をあえて読まずに、自分の言葉で「めがねどこにおいたかなぁ」と言った。黙るまで待つ新しい方式で「メガネどこに置いたかな」と一回で聞き取れた。
  - 自分は「すみません」と送ったが、Claude の返事は「むしろ一番ほしかった結果です」。決まった言い方ではなく、本人の言葉で通ったから。
  - 決めたこと: 言い方は人それぞれで、用意した決まり文句どおりには話してくれない。意味のくみ取りはキーワードの一致だけに頼らず、Claude にも任せる。
- **16:05 方針を変えた: 「アプリの方から声で聞いてほしい。テキストを読むのも一苦労」。** 3回のテストを見て、父に画面を読ませる作り自体をやめることにした。
  - **16:06 新しい会話の画面（/talk）を公開。** 画面いっぱいの「さわってください」を一回押すと、アプリが「どうしましたか？」と声で聞き、そのまま返事を待つ。眼鏡の話なら「眼鏡を探しているんですね。一緒に探しましょう。」、よくわからなければ「眼鏡を探していますか？」と聞き直し、声か大きな「はい／いいえ」ボタンで答える。アプリが話している言葉は大きく表示し、聞いている間はマイクの印がふくらむ。
  - iPad では最初の音声を鳴らすのに一回のタップが必要なので、「画面を一回さわる」を始まりの合図にした。
  - 読み上げと聞き取りを順番につなぐ部品（lib/voice.ts）を作った。
  - まだわからないこと: アプリが話し終わってから自動で聞き取りを始めるのを iPad が許すか。「〜と聞こえました」の読み上げが父に聞こえる音量・速さだったか。
  - 振り返ると、1時間ほどで「画面に文字を出す」→「話してほしい言葉を画面に出す」→「アプリから話しかける」と考えが進んだ。実際に使う人に試してもらうことの大切さ。
- **16:16 /talk を iPad で試した。感想は「いい感じです」。**
  - 「眼鏡」と言わずに「困った」とだけ言うと、アプリが声で「眼鏡を探していますか？」と聞き返した。キーワードがなくても、こちらから確かめる流れが動いた。
  - 聞き直しのあと、「はい／いいえ」の選択ボタンが出て、ボタンを押して先に進んだ。聞き直しでは、声でもボタンでも答えられるよう、いつもボタンを出す作り。
  - 心配していた「アプリが話し終わったあと、自動で聞き取りを始める」動きも iPad の Safari で動いた。「どうしましたか？」のあと、「困った」をそのまま聞き取れたのがその証拠。アプリから話しかけて返事を聞く形が成り立った。
- **16:19 初めて、声だけで最後まで会話が通った（動画で記録）。**
  - アプリ「どうしましたか？」→ 父「ちょっと困ってるんです」→ アプリ「眼鏡を探していますか？」→ 父が「はい」を押す → アプリ「眼鏡を探しているんですね。一緒に探しましょう。」
  - 「眼鏡」という言葉が一度も出なくても、アプリの方から確かめて、探す流れの入口までたどり着けた。初日の終わりに、この作品の形が見えた瞬間。
  - 動画を見ると、父は眼鏡を頭にのせたまま試していた。「思い出せないときは、まず頭の上を確かめる」という順番を決めた理由が、そのまま映っていた。記事の書き出しに使えそうな場面。
  - 注意: 動画のコマには家族の実名や電話番号のメモが写っているので、画像はそのまま公開しない。
#### 予定を前倒しして、探す流れを作り始めた

- **16:3x 「続きやりませんか？」。** 声のめどが立った勢いで、11/4 にやる予定だった「一か所ずつ確かめる流れ」に初日のうちに取りかかった。
  - 候補の場所はサンプルで11か所。順番と点数はプログラムで決める（lib/places.ts、lib/rank.ts）。頭の上・首元・ポケットのような体のまわりはいつも先に、そのあと時間帯と、過去に見つかった回数で点数を足す。
  - Claude の並べ替え（/api/rerank）: Claude Haiku を使い、深く考える機能は切り、考える深さは最小、4秒で打ち切り、やり直しはしない。返事は候補の ID の中からしか選べない形（structured outputs の enum）に縛り、さらに受け取ったあとにも候補にないものを取り除き、足りない分はプログラムの順番で埋める。二重の歯止め。
  - API キーがないときや失敗したときは、プログラムの順番のまま進む。キーなしでも動くことを確かめた。
  - 待ち時間を隠す工夫: Claude の返事を待つあいだに「一緒に探しましょう」を読み上げる。父には待たされている感じが出ない。
  - 探している途中で父が手がかり（「さっき新聞を読んでいた」など）を話したら、残りの場所を並べ替え直す。
  - 4か所確かめるごとに「続ける／休む」を選べる。探した記録はまず iPad の中（localStorage、lib/history.ts）に残す。
  - API キーは Vercel の環境変数に自分で入れる（リポジトリには入れない）。
- **22:14 夜、iPad で一か所ずつ確かめる流れを試した。** Claude の並べ替えが実際に動いた（返事まで 1729 ミリ秒、サンプルの「居間のテーブル」を一番に挙げた）。直してほしい点が3つ見つかった。
  1. **ゆっくり話すと途中で切られる。** 「さっき新聞を読んでたけど眼鏡」の途中で聞き取りが止まった。父はゆっくり、間をあけて話す。昼に決めた「1.5秒黙ったら区切る」では足りなかった。少し黙ったくらいでは止めないようにする。
  2. **「はい」だけで「あったね」になった。** 見つかった場所まで覚えてしまった。でも「はい」は、ただの相づちのつもりで言うこともある。見つかったと判断するのは「あった」「あったよ」などのときだけにするか、「見つかりましたか？」ともう一度確かめる。画面にも大きな「あった」「なかった」のボタンを置く。
  3. **実際の家の場所を入れたい。** サンプルの場所ではなく、実家の本当の置き場所や、その時間帯の習慣を使いたい。ただし公開リポジトリには入れず、父の iPad の中だけで使えるようにする。
  - **すぐに直した。**
    1. 区切るまでの無音を 1.5秒 → 3秒に。さらに「〜けど」「〜て」のように、まだ続きそうな終わり方のときは 5秒待つ（lib/voice.ts）。
    2. 「あった」「ありました」などのときだけ見つかった扱いにする。「はい」「うん」だけのときは「見つかりましたか？」と確かめ直す。ボタンも「あった／なかった」にした（lib/normalize.ts）。
    3. 実家の場所は、iPad の設定画面（/settings）から入れて、その iPad の中（localStorage）にだけ保存する。リポジトリにもサーバーにも残らない。書き方は「場所の名前｜確かめ方｜怪しい時刻」。怪しい時刻の前後は点数を足す（たとえば毎日決まった時刻にすることがあれば、その場所を先に）。Claude の並べ替えにも、場所の名前と今の時刻を渡すようにした。
  - 気づき: 「はい」の意味ひとつでも、言葉どおりに受け取ると高齢の人の会話ではずれる。見つかった記録は次の候補の点数に効くので、まちがって覚えると、そのあとずっとずれる。
- **初日のまとめ。** 一番不安だった声の聞き取りと読み上げが iPad で動き、「アプリから話しかける」形まで進んだ。さらに予定を前倒しして、11/4 分の「一か所ずつ確かめる流れ」と Claude による並べ替えにも手をつけた。

## Claude Code の機能をどこで使ったか

| 機能 | 何のために | いつ入れたか | メモ |
|---|---|---|---|

## 使ったモデルと理由

| 用途 | モデル | 理由 |
|---|---|---|
| 父の話から候補の順番を入れ替え、理由を一言 | Claude Haiku 5.5（深く考える機能は切る、考える深さ最小、4秒で打ち切り） | 返事の速さを優先。候補の ID 以外は選べない形に縛り、失敗時はプログラムの順番で続ける |

## 記事に使えそうな言葉・場面

- 「いきなりコードを書かずに、まず案を見せて」から始めた。
- 「必ず見つかる」とは言わない、という決まり。
- AI に場所を当てさせるのではなく、プログラムが出した候補の順番だけを任せる、という分担。
